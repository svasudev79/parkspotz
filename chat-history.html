npm run dev             # runs on :3000

Three layers, in order of importance for a one-day build: a scripted manual walkthrough of the whole journey, a few targeted checks on the rules that are easy to get wrong, and optionally an automated version of the walkthrough.

1. End-to-end walkthrough (the acceptance test)

Use two browser windows, one normal and one private, so you can be logged in as an owner and a driver at the same time. Start from seed data: a handful of Bangalore parking spaces near one known destination (say MG Road metro).

1OwnerSign up, log inLands on owner home
2OwnerAdd a space near the destination: 2 slots, ₹40/hour, 08:00–22:00Appears in "my spaces"
3DriverSign up, log inLands on search
4DriverSearch the destination, 1 km radius, tomorrow 10:00 for 2 hoursNew space shows on map and list, "2 slots available"
5DriverShrink radius to 500 m, then search a far-away destinationSpace drops out when out of range
6DriverBook it and pay with Razorpay's test card or test UPI IDBooking becomes confirmed, receipt opens with ₹80 and a QR code
7DriverRepeat the same searchNow "1 slot available"
8DriverSave the receipt as PDF; open "My bookings"Booking is listed, receipt reopens
9OwnerOpen the QR's verify linkShows the booking as valid
10OwnerOpen stats1 booking, 2 hours, ₹80 for the day

Steps 1–5 cover every success metric in your spec; 6–10 cover the booking and payment half.

2. Targeted checks for the risky rules

  • Last slot: set a space to 1 slot, have two drivers book the same window. The second must be refused.
  • Overlap logic: with that slot booked 10:00–12:00, a search for 11:00–13:00 shows 0 available, and 12:00–14:00 shows 1.
  • Abandoned payment: start a booking, close the Razorpay window without paying. The slot is held, then free again after 10 minutes.
  • Failed payment: use Razorpay's test failure option. Booking must not become confirmed.
  • Opening hours: a booking outside 08:00–22:00 is rejected.
  • Access control: a driver can't open owner pages, an owner can't see another owner's stats, and a made-up QR token shows as invalid.
  • Mobile: repeat steps 3–8 on a phone, or at phone width in the browser.

3. Things that affect how you test

  • Payments cost nothing. In Razorpay test mode no real money moves, and their docs list the test card numbers and UPI IDs to use.
  • QR scanning needs a reachable URL. The QR encodes a link, and a phone can't open localhost. Either test after deploying (block 8), or copy the verify link into the browser by hand while local.
  • Time-dependent cases like the 10-minute expiry are quicker to test by temporarily setting the hold to 1 minute.

4. Optional automation

Once the app runs, I can drive the walkthrough myself in the built-in browser and report which steps pass, which is the fastest check on the day. For something repeatable, the same ten steps can be written as a Playwright test, plus a few API tests for the section 2 rules. Given the one-day budget, I'd only automate the last-slot and overlap checks, since those are the ones most likely to break silently later.

42	
43	```

65	Key design decisions:
66	
67	- **Slots are a count, not individual records.** A space has `total_slots`; a booking reserves any one slot. Numbered slots can come in Phase 2.
68	- **Availability** for a time window = `total_slots` − bookings in `pending` or `confirmed` status whose time range overlaps the window.
69	- **No double booking.** Creating a booking runs in a transaction that locks the parking space row, recounts overlapping bookings, and inserts only if a slot is free.
70	- **Unpaid bookings expire.** A `pending` booking holds a slot for 10 minutes; after that it stops counting against availability, which releases the slot.
71	- **Times** are stored in UTC and displayed in IST.

73	## 4. Key flows
74	
75	**Search**
76	1. Driver types a destination; Places Autocomplete returns its lat/lng.
77	2. Driver picks a radius (e.g. 500 m, 1 km, 2 km) and a date/time/duration.
78	3. API returns active spaces within the radius (Haversine distance in SQL), each with distance, price and slots available for that window.
79	4. Results are shown as map pins and as a list sorted by distance; the two views stay in sync.
80	
81	**Book and pay**
82	1. Driver selects a space and confirms the time window; the API creates a `pending` booking and a Razorpay order.
83	2. Razorpay Checkout opens in the browser.
84	3. On success the API verifies the payment signature, then marks the booking `confirmed`.
85	4. Driver lands on the receipt page.
86	
87	**Receipt and QR**
88	- Receipt shows space name, address, date, time window, amount, booking reference and a QR code.
89	- The QR encodes a verification URL containing the booking's random `qr_token`.
90	- The receipt is saved by the browser's print-to-PDF; it also stays available under "My bookings".
91	
92	**Owner onboarding and operations**
93	1. Owner fills a form: name, address (Places Autocomplete, with a draggable map pin), type, ownership, number of slots, price per hour, opening and closing time.
94	2. Owner dashboard lists their spaces and today's bookings.
95	3. At entry the owner scans the driver's QR with a phone camera; it opens the verify page, which shows whether the booking is valid for that space and time.
96	4. Stats page shows bookings, hours booked and revenue by day, week and month.
